# Процесс изменения правил

Этот файл — канонический источник для:
- правил гармоничности;
- шаблона «ИСКЛЮЧЕНИЕ»;
- формата ответа агента.

Другие файлы (`00_README.md`, `03_rules.md`, `05_protocols.md`) ссылаются сюда.

Законы проекта в `01_laws.md` имеют наивысший приоритет.
Изменение правил не может противоречить Законам 1–13.

## Когда можно предложить изменение

Правило можно предложить, если:

- проблема повторилась минимум дважды;
- есть риск потери данных, безопасности или времени;
- текущее правило мешает развитию;
- появился новый обязательный бизнес-сценарий;
- изменились ограничения проекта;
- изменился домен данных или основной источник истины;
- появилась новая юридическая норма, влияющая на продукт;
- требуется безопасная миграция данных из внешней системы.

## Формат предложения

```text
ПРЕДЛОЖЕНИЕ ПРАВИЛА
Название: ...
Проблема: ...
Предлагаемое правило: ...
Почему нужно: ...
Домен данных: ...
Источник истины: ...
Как проверить соблюдение: ...
Как откатить: ...
Приоритет: P0 / P1 / P2 / P3
Срок пересмотра: ...
```

## Жизненный цикл правила

```text
Proposal → Agreed → Active → Deprecated
```

| Статус | Значение |
|---|---|
| Proposal | Предложено, обсуждается |
| Agreed | Согласовано, но ещё не внедрено |
| Active | Действует и обязательно к соблюдению |
| Deprecated | Отменено или заменено |

## Условия перевода в Active

- [ ] Понятна проблема.
- [ ] Правило не противоречит законам проекта.
- [ ] Определён домен данных и источник истины.
- [ ] Понятно, как его проверять.
- [ ] Понятно, как его откатить.
- [ ] Указан срок пересмотра.
- [ ] Изменение внесено в нужный файл.
- [ ] Решение зафиксировано в `07_decision_log.md`.

## Юридические изменения

Добавление, обновление или использование юридической нормы
оформляется через протокол `ПРАВО`.

Превращение юридической нормы в требование продукта
оформляется через протокол `КОМПЛАЕНС`.

Юридическая норма может стать правилом продукта только если:

- указан официальный первоисточник;
- указаны юрисдикция, редакция и статус нормы;
- норма не утратила силу и не заменена;
- понятно, как требование проверяется в продукте;
- понятно, как требование откатывается;
- при необходимости проведена проверка юристом.

AI не выдаёт юридическое заключение
и не рекомендует юридически значимое действие.

## Миграция данных

Миграция данных из внешней системы, включая 1С,
оформляется через протокол `МИГРАЦИЯ_ДАННЫХ`.

До запуска фиксируются:

- источник данных;
- сопоставление полей;
- правила трансформации;
- правила разрешения конфликтов;
- тестовая выгрузка;
- результат dry-run;
- план отката;
- подтверждение запуска.

## Как отменить правило

```text
ОТМЕНА ПРАВИЛА
Название: ...
Причина отмены: ...
Что заменяет: ...
Дата отмены: ...
```

## Временное исключение

Если правило мешает срочной задаче:

```text
ИСКЛЮЧЕНИЕ
Правило: ...
Задача: ...
Причина: ...
Срок действия: ...
План возврата к правилу: ...
```

Исключение не отменяет правило.

Исключение не может отменять Закон 4 «Безопасность прежде удобства»,
Закон 8 «Откат важнее фичи», Закон 12 «Разделение источников истины»
или Закон 13 «Право отделяется от рекомендации».

## Правила гармоничности

Новое правило должно:

- решать реальную проблему;
- быть понятным;
- быть проверяемым;
- иметь откат;
- не создавать лишнюю бюрократию;
- не создавать второй источник истины для одного домена данных;
- не превращать юридическую информацию в юридическую рекомендацию.

Если правило не проходит хотя бы одно условие, оно остаётся в статусе `Proposal`.

## Формат ответа агента

Канонический формат ответа агента:

```text
1. План
2. Действия
3. Проверка
4. Риски
5. Откат
6. Следующий шаг
```

## Связь с реестром функций

Изменение статуса функции (добавление/исключение из скоупа, приостановка, отмена) фиксируется в `scope_registry.md` по правилам из `03_rules.md`.

## Связь с журналом решений

Каждое согласованное изменение правила, закона, сущности,
источника истины или скоупа фиксируется в `07_decision_log.md`.

Исторические записи не переписываются задним числом:
изменение оформляется новой связанной записью.
